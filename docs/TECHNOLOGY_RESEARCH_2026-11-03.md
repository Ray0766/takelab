# Technology research: synchronization and take selection

Reviewed **2026-11-03** against TakeLab commit `3ed9634`. This records the recommendation and isolated feasibility experiment **before implementation**; at that point production code and dependencies were unchanged. The subsequently authorized implementation and its separate validation are recorded in [Source-frame inspection](SOURCE_FRAMES_2026-11-03.md). Do not treat the isolated probe below as an integrated performance benchmark.

## Recommendation

Build **source-frame inspection with linked evidence** first: keep the native nine-take overview, then inspect two shortlisted takes using real source presentation timestamps, linked magnification and source-frame stepping. Use WebCodecs through a small, lazy-loaded Mediabunny adapter in a dedicated worker. Preserve native playback as the fallback.

Next, add **optional proxy previews with source-frame confirmation** if realistic multi-stream tests show decoding pressure. Add an explicit event-anchor alignment action alongside this work. Evaluate automatic issue navigation later, beginning with inexpensive signal-based candidates and human confirmation. Do not make an automatic aesthetic score decide the winner.

This prioritizes a verifiable capability—returning to the actual frame behind a decision—over an unmeasured claim that a new decoder or model makes selection faster.

## Baseline and the actual gaps

- `src/useTransport.ts` follows a source media clock, corrects drift above 100 ms, coordinates buffering and freezes the actual media position on pause. Its step operation advances by `1 / review FPS`, not the next source presentation timestamp (PTS).
- The prior three-run [UI synchronization receipt](evidence/ui-20261103/sync-summary.json) measured 1× presented-timestamp p95 of 41.7–58.3 ms on two synthetic 1080p sources. The earlier [83.3 ms miss](evidence/sync-after-run2.json) against the 80 ms target remains relevant. These are callback-based observations, not external measurements of screen scanout.
- Nine-way acceptance currently uses 640×360 material. Nine 1080p/4K sources and ordinary-laptop capacity remain unverified. The existing Windows host has a Core Ultra 9 285K, approximately 63.3 GiB RAM and an RTX 5090; that does not prove Chromium uses hardware video decoding.
- Offsets align source time, but separately generated actions can happen at different moments. Clock alignment, source-frame identity and event alignment are three different problems.
- Current exports preserve winner → reason → source-time observation → generation record. They do not yet include verified source-frame snapshots or source-content fingerprints. Relinking uses metadata rather than a content hash.
- A comparison recording is real-time and silent. Its historic 141 frames for a nominal six-second, 24 fps capture illustrates why it is a review copy, not a frame-exact master.

For the established baseline and limits, see [validation](VALIDATION.md) and [release follow-up](RELEASE_CHECK_2026-11-03.md). No old benchmark was rerun and relabeled as new evidence for this research.

### What is actually new or newly practical

**WebCodecs and workers are established APIs, with an evolving specification.** The current W3C publication checked here is the [2 November 2026 Working Draft](https://www.w3.org/TR/2026/WD-webcodecs-20261102/). It does not require any particular codec. Chrome's [implementation guide](https://developer.chrome.com/docs/web-platform/best-practices/webcodecs) explains worker-based frame handling; container demuxing and muxing remain separate concerns.

**Mediabunny lowers the amount of media infrastructure we would have to write.** Its [sample retrieval API](https://mediabunny.dev/guide/media-sinks) defines a concrete rule: return the last frame whose presentation timestamp is at or before the requested time, and provides ordered iteration. That addresses VFR and source stepping directly. Its [July 2026 quantizer support](https://mediabunny.dev/blog) is also relevant to controlled proxy quality; the April HLS addition is not needed for local files. The project is actively changing, so upgrades should be pinned and regression-tested rather than tracking `latest`.

The release page showed **1.65.1** and the tagged source declared MPL-2.0. At the actual npm query, `1.65.1` returned 404 and the registry's latest package was **1.65.0**. The experiment therefore uses **1.65.0**, not an assumed installable release. See the [upstream releases](https://github.com/Vanilagy/mediabunny/releases) and [pinned source](https://github.com/Vanilagy/mediabunny/tree/v1.65.0). The fetched archive was 2,301,012 bytes; the unminified full ESM bundle used in this isolated experiment was 1,560,416 bytes. Neither number estimates the final tree-shaken app payload.

Mediabunny is **MPL-2.0**, not MIT. If adopted, preserve its license and a source-availability notice in distributions; changes to covered files require separate attention. TakeLab's own source remains separately licensed. [Mozilla's FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/) distinguishes file-level obligations and combined works. The probe downloads the package locally; it does not vendor its code into this repository.

**Transformers.js v4 is a relevant 2026 improvement for optional local ML.** Its [February 9 announcement](https://huggingface.co/blog/transformersjs-v4) describes a rewritten WebGPU runtime and model-asset inspection/caching APIs. The [repository package manifest](https://github.com/huggingface/transformers.js/blob/main/packages/transformers/package.json) checked here declares 4.3.2, Apache-2.0, and a pinned development ONNX Runtime Web dependency. This is a source-manifest observation, not an installed or benchmarked dependency. Model weights have their own licenses; runtime compatibility does not establish model correctness or speed. Vendor benchmark multipliers are not TakeLab estimates.

**MediaCapabilities, OPFS and proxy workflows are mature baselines, not 2026 inventions.** [MediaCapabilities](https://developer.mozilla.org/en-US/docs/Web/API/MediaCapabilities/decodingInfo) supplies configuration-level support/performance hints. It does not promise nine simultaneous decoders. [OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system) offers private file storage and worker-friendly access but is still quota-bound and cleared with site data. Keep project metadata in IndexedDB; use OPFS only for regenerable caches initially. The [File System Access API](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access) can avoid copying originals into browser storage on supported browsers, but adds permission renewal/missing-file handling; it does not improve frame timing by itself.

### Why proxies need an original-frame path

Proxy compression or resizing can hide flicker, small hand defects and texture changes. Do not silently lower frame rate, interpolate motion, crop images or normalize every input to constant FPS. Preserve presentation times or store an explicit proxy-to-source mapping, normalize track start offsets/edit lists, and always record evidence against the original asset. Color/HDR transformations must not be presented as faithful color comparison.

Create proxies serially or with tightly bounded concurrency when playback is idle; conversion and inference compete with playback. Support cancel/retry, cache invalidation by source identity and settings, quota errors and a visible original/proxy state. A native FFmpeg/Resolve-produced proxy is the mature comparison baseline. [Resolve's official proxy workflow](https://www.blackmagicdesign.com/products/davinciresolve/collaboration) already links proxies to originals; TakeLab's opportunity is making that process lightweight for cross-source take selection.

Do not introduce ffmpeg.wasm as the default nine-video transcoder without a benchmark. Its [official performance page](https://ffmpegwasm.netlify.app/docs/performance/) uses old Chrome 116 / core 0.12.3 data; it demonstrates overhead in that historical setup, not a current speed ratio for this project. Native FFmpeg remains useful for fixture generation and an optional external workflow.

The [current PhysTrace README](https://github.com/PhysTrace/PhysTrace) defaults to a different, larger model configuration than the paper (Qwen3.8-27B plus PE-AV-Large). Reproducing the paper would require pinning its exact setup rather than assuming the current default is equivalent. No models were downloaded, no paid inference ran, and no user media was uploaded.

For a practical first assistant, compare simple luminance-change/freeze candidates against a small optional model. Label outputs as **machine suggestions**, attach actual source intervals, and require acceptance before adding them as decision evidence. Record method/model version and allow dismissal. Deliberate flashes, cuts, stillness, occlusion and stylized deformation must be negative examples. A sparse sampler can miss a one-frame error; neither a low score nor a missing alert proves validity. Analysis must pause while it harms playback.

Semantic alignment should propose anchors, not silently time-warp playback. Retiming can hide the motion quality being judged. Audio cross-correlation is appropriate only when sources share the same underlying audio; independently generated speech/music often does not.

## Bounded local experiment

The experiment was scoped before running: verify sample identity and source timestamps on two original synthetic files, with native HTML video as a baseline. It does not measure multi-stream playback, user speed, GPU usage or integrated UI latency.

**Environment:** the same Windows host described above; Node 24.18.0, FFmpeg 8.1, Playwright Chromium 156.0.8078.4, headless. Fresh browser context and a private ephemeral localhost server; the app's browser storage was untouched.

**Inputs:** two 640×360 H.264 clips derived from 60 uniquely coded RGB frames. One is constant 30 fps (60 frames); the other changes from 30 to 10 fps by retaining original timestamps (40 frames). Both contain B-frames. Eight black/white patches encode each original frame number so that checking metadata alone cannot pass with the wrong pixels. FFprobe independently lists the expected presentation order.

**Queries:** 20 nonmonotonic requested times per file, including points immediately before/after source-frame boundaries. The oracle is the last FFprobe PTS ≤ requested time, with a 2 µs comparison allowance for decimal representation. The worker decodes, draws to an OffscreenCanvas, checks the binary pixels and closes each sample. Native `<video>` seeks, waits for a video-frame callback, then reads the same pixels. Both use local Blob data. The worker also enumerates every sample in presentation order.

| Check                                               | CFR     | VFR     |
| --------------------------------------------------- | ------- | ------- |
| Worker/WebCodecs: correct PTS and actual frame code | 20 / 20 | 20 / 20 |
| Native HTML video: correct actual frame code        | 20 / 20 | 20 / 20 |
| Worker enumerated PTS match FFprobe                 | 60 / 60 | 40 / 40 |
| Missing native frame callbacks                      | 0       | 0       |

The receipt retains worker p95 retrieval/readback of 6.3 / 5.1 ms and native p95 seek/callback/readback of 18.0 / 17.7 ms. **These endpoints differ**: worker timing ends at offscreen readback, while native timing includes compositor callback scheduling. Small cached clips on a powerful host also favor both. Do not turn these numbers into a playback speedup claim.

The capability probe returned `VideoDecoder`, `OffscreenCanvas`, `navigator.gpu` and OPFS API presence. A separate H.264 1080p30 / 8 Mbps MediaCapabilities query returned `supported: true`, `smooth: true`, `powerEfficient: false`. API presence is not a successful WebGPU adapter test; the capabilities result is not proof of hardware decode or concurrent capacity.

**Interpretation:** native seeking is an adequate baseline in these cases. The tested advantage of the new path is access to ordered decoded samples and verified PTS, not better native-seek accuracy. For example, on the VFR fixture's 10 fps portion, thirteen 24 fps review positions from 1.0 through 1.5 seconds map to only six distinct source frames. That is an exact calculation from the fixture timestamps: nominal stepping cannot mean “next source frame.” Explicit sample navigation can.

An initial harness run failed before browser measurement because the FFmpeg filter expression was incorrectly escaped; the quoting was corrected. There was one completed browser experiment, not a repeated performance study.

Evidence: [complete receipt](evidence/technology-20261103/frame-access.json), [reproducible probe](../scripts/research-frame-access.mjs). The research package stays under ignored `.local/technology-probe`; no production lockfile changed. Its tarball integrity was:

## Proposed first delivery and acceptance

The demonstration should be: **nine takes → shortlist two → align an action → inspect actual source frames at the same review moment → magnify a defect → attach the frame and observation → select a take → export and reopen its evidence and generation record**. This extends the project's existing differentiator instead of adding a separate AI dashboard.

Implement a small `FrameReader` boundary rather than replacing `useTransport`: original source → format/track metadata → ordered samples → bounded worker cache → paused inspection surface. Both candidates must finish the requested seek before the inspection pair is presented. Discard stale work when the user scrubs again. Audio and continuous overview playback remain on the existing path.

Markers need the original source identity, track and actual PTS in addition to the existing source-relative seconds. Normalize container start times/edit lists explicitly; a decoder's sample index is not a universal frame number. Keep original media and generation records authoritative. Export verified snapshots with their provenance and source references, and make unsupported-source fallback explicit.

Mixed 24/30/VFR sources generally do **not** have frames with identical PTS. Define alignment as selecting the sample covering each source's requested review time, not forcing equal frame indices or inventing intermediate frames. Even a shared canvas cannot guarantee physical monitor scanout synchronization.

Predeclare the next implementation gate before measurement:

- Correct decoded frame identity at boundaries, repeated/backward steps, offsets, loop endpoints and VFR changes; add 24/30/60 fps, long-GOP, rotated and unsupported inputs. Zero wrong-source or stale-frame results in the fixture set.
- Pause → observation → snapshot → portable archive → restore must resolve to the same original frame and take. Deleting or replacing a source must not silently reuse another frame's evidence.
- On a named ordinary target laptop, propose warm 1080p pair inspection p95 ≤200 ms and cold/long-GOP seek p95 ≤750 ms. These are **future targets**, not achieved measurements. Preserve the current playback acceptance targets; do not relax them to accommodate the new feature.
- Bound decoded-frame ownership, close samples and cancel pending reads. A 1920×1080 RGBA frame is about 8.3 MB before overhead; holding six for each of two takes is already about 99.5 MB. This is allocation arithmetic, not measured browser memory. Count native/GPU resources as well as JS heap.
- For proxies, compare originals versus proxies on 1/4/9 streams with the same source moments; measure readiness time, sync spread, drop rate, browser/GPU memory, transcode time and cache size. An API support response is not the acceptance test.
- For an assistant pilot, use at least 60 consented/distributable clips, including deliberate effects and clean examples. Report per-category precision, recall, false suggestions per minute, interval overlap, review time, model download size, inference latency and memory. A suggested small-pilot gate is ≥80% precision and recall for narrowly defined supported defect classes plus ≤1 false suggestion/minute; this is not a universal quality standard or sufficient market evidence.
- Compare human workflow time and missed defects against the current TakeLab and an ordinary player plus notes. Counterbalance task order; do not use repeated familiarity with the synthetic demo as evidence of improved creative decisions.

## Scope and remaining uncertainty

This research checked official browser/library material, author papers/code and existing project measurements. [Frame.io](https://help.frame.io/en/articles/9952618-comparison-viewer) and Resolve are mature baselines: synchronized review, comments and proxies are not novel by themselves. TakeLab's proposed gain remains the low-friction connection between the chosen take, original frame, observation and recipe. No competing product was newly usability-tested here.

The small experiment does not establish 1080p/4K WebCodecs inspection performance, nine-way scheduling, sustained memory behavior, audio synchronization, Safari/Firefox support, HEVC/HDR fidelity or better human choices. No AI detector was run. The research justifies a bounded hybrid inspection implementation; it does not justify a full playback rewrite or an automatic winner selector.
